# Live conversation mode (hands-free)

One tap, then the pilgrim just talks. The page listens, answers aloud, listens again, until "thank you" / End / 25 s of silence.

## Files (all new, nothing existing edited)
- `app/addons_live.py` router: `POST /api/live/turn` (multipart `audio`, `uid`, `lang`, `session_id`; optional `text`) and `POST /api/live/prompt` (form `kind=greeting|nudge|goodbye`, `lang`, `session_id`).
- `app/tests/test_addons_live.py` (13 tests, Sarvam mocked). Whole suite: 189 passed.
- `app/addons_ui/live.js` (class `LiveSession`, plus `AddonsLive.init(root, opts)`), `live.html` (fragment), `live.css`, `live_demo.html` (standalone page).
- Test tooling (not part of the app): `_tools/live/` (make_live_wav.py, live_app.py, drive.cjs, http_conv.py).

## Integrator steps
1. `main.py`: `from addons_live import router as live_router` and `app.include_router(live_router)` (or add `"addons_live"` to the `_mount` list near line 365).
2. Put `live.html` where the voice screen goes; include `addons_ui/live.css` and `addons_ui/live.js` (serve them from /static or copy them). Then `AddonsLive.init(document.getElementById('ad-live'), {uid: <pilgrim id>, lang: () => currentLang})`. `lang` can be a string or a function. The page remembers a language switch made by voice (`session.lang`); the next language-picker change is sent as the `lang` field, but once the pilgrim switches by voice the server keeps that language for the session.
3. Env vars: none new. Uses SARVAM_API_KEY like the rest. HTTPS is required on phones for the microphone.
4. Events for your own UI: `s.on('state'|'level'|'caption'|'turn'|'end'|'error', fn)`. States: idle, listening, hearing, thinking, speaking, error.

## Front end design
- One `getUserMedia` stream (echoCancellation, noiseSuppression, autoGainControl on) kept for the whole session; AudioContext, the single `<audio>` element (unlocked with a silent clip) and the wake lock are all started inside the first tap. UI text says "Tap once to start talking" and explains why.
- VAD in the browser, AudioWorklet (ScriptProcessor fallback), 21 ms frames: noise floor measured in the first 500 ms (in quiet: the greeting waits for it) and updated while idle; speech starts after about 150 ms above max(3x floor, floor+0.01), ends after 900 ms below max(1.8x floor, floor+0.005); minimum 350 ms voiced, maximum 12 s (cut and sent, listening continues); 400 ms pre-roll; all values are options.
- Recording choice: raw PCM ring buffer encoded to a 16 kHz mono 16-bit WAV in JS (not MediaRecorder). Reason: MediaRecorder gives webm on Chrome and fragmented mp4 on iPhone Safari, needs restarting per utterance (loses the first syllable) and has container quirks; PCM gives the same bytes everywhere and an exact pre-roll. Cost about 32 KB per second of speech.
- Turn taking: while the reply plays, the floor is not updated and barge-in needs the mic above max(1.5x on-threshold, 2.5x the running echo level) for 300 ms; then the reply stops and the new utterance is recorded (pre-roll included). If the pilgrim speaks while a reply is still being computed, that utterance is queued and sent right after. Silence: nudge after 8 s (fetched from /api/live/prompt, cached audio), quiet end after 25 s ("Tap to talk again").
- Level 0..1 for a meter or breathing circle (`--lv` CSS variable): mic level while listening, the reply's own voice envelope (computed from the WAV, so audio is not routed through Web Audio and the iPhone silent switch does not mute it) while speaking.
- Robustness coded: permission denied / no mic (clear message), tab hidden (utterance dropped, context resumed and wake lock re-requested on return), mic track ended, AudioContext `interrupted`, network error (retry once, then caption plus browser speech "I could not reach the server"), empty or noise utterances (server returns `ignored`, nothing is spoken), autoplay blocked (message), long speech (12 s cap).

## Back end design
- Per-session state (idle, ask_when, ask_party, confirm, booked, ended) in memory, 1 h TTL.
- Order: goodbye, language switch, repeat, cancel, change time, then the state's own question; keyword rules first (directions.keyword_intent, parse_when, say_time, respond), Sarvam chat second (directions.understand when idle, and a small slot-filling JSON prompt when a state answer is not understood). Unclear input gives a short rephrased question and never books; two misses on "how many people" assume one person; unclear confirm asks yes or no again.
- Booking goes through `directions.book_slot` -> `slots.book` (so the Flagsmith `slot_mode` applies); a changed time cancels the old booking first. Age ("my mother is 70") goes through `directions.set_age_trait` -> `flags.set_traits`.
- Replies in the six languages for the dialogue prompts (written by me, not reviewed by native speakers: please have the Telugu and Malayalam lines checked). TTS cache keyed by (lang, text), so fixed prompts cost 0 ms; the nine fixed prompts of a language are pre-warmed in the background after its first turn.
- Response: `{transcript, reply_text, audio_base64, lang, state, end_session, slot, latency{stt_ms,llm_ms,tts_ms,tts_cached,total_ms}, ignored, intent, via, notice}`. Sarvam credit / error problems come back as `error:true` with the usual notice text.

## Verified for real
- Throwaway app `_tools/live/live_app.py` (imports main.app, includes my router, serves addons_ui) on port 8741 with real Sarvam keys, driven by headless Chrome for Testing (own profile `_tools/tmp-profile-live`) using a Telugu/Malayalam WAV made with Sarvam TTS + silences + background noise + one 120 ms click burst (`_tools/live/audio/live_conv.wav`, marks file next to it).
- **Browser, one tap only, no other clicks**: the AudioWorklet VAD found each utterance by itself (floor measured 0.002); the full booking ran hands-free: "naaku slot kavali" -> "when?" -> "repu udayam" -> "how many?" -> "iddaru" -> "Tomorrow 6, Base Camp, for 2 people. Shall I book it?" -> "avunu" -> booked and spoken. Replies played through the single `<audio>` element. The click burst was not detected as speech (0 false triggers in the browser runs after I fixed one: an earlier version used the smoothed level and triggered on the burst, now raw frame level). Barge-in worked once: "iddaru" spoken over the nudge stopped the nudge and was captured.
- Latency (speech end to first audio, browser): 0.32 to 0.38 s for cached prompts, 2.1 to 3.4 s when the reply needs fresh TTS (STT 0.3 to 1.7 s, TTS 1.6 s). Without TTS the Sarvam STT call alone is about 0.3 s.
- **Server, real STT/TTS, same WAV sliced into the same session over HTTP** (`http_conv.py`): all 6 utterances plus the burst handled; burst -> `ignored:true`; thank you -> `end_session:true`; the language hint applies to Telugu STT. Misses found and fixed from this: Telugu long-vowel "iddaru" variant, wait question during the read-back.
- Detection misses: 0 of the 4 utterances in the clean browser runs; false triggers: 0 after the fix (the 7 utterance/ignored lines in the first run were from the broken timing, see below).

## Not verified / known problems (be honest)
1. **Chrome's fake microphone device (`--use-fake-device-for-media-stream --use-file-for-fake-audio-capture`) hangs getUserMedia in this macOS session** (same as the earlier voice test lane noted), so the browser test feeds the WAV to the page through `testSource` (an in-page AudioBufferSource in the same AudioContext, real worklet, VAD, WAV encoding, upload and playback). `getUserMedia` constraints, permission-denied handling, wake lock, and iPhone Safari were NOT exercised.
2. In headless Chrome the AudioContext render clock slows to about 0.25x after about 28 s (always at the same moment, after the first long fresh-TTS reply, even with barge-in, nudge and UI repaint switched off), so later speech arrives too slowly: the Malayalam wait question and the thank-you were not completed in the browser (4 turns done). I could not tell whether this is the headless audio sink or a bug in my loop; check on a real phone first. The same turns were verified over HTTP (above).
3. iPhone: PCM capture while an `<audio>` element plays may change the audio route (earpiece vs speaker); echo cancellation quality and barge-in thresholds are untested on real hardware. Tune `bargeRatio`, `onAbs`, `silenceMs` on a phone.
4. Speech to text writes Telugu in non-standard spellings sometimes ("re pokodayam" for "repu udayam"); the Sarvam chat fallback handles some of it, not all. The Telugu phrase for 'two people' is matched by stem.
5. Streaming: docs.sarvam.ai lists a realtime STT WebSocket (api-reference/speech-to-text/transcribe/realtime/ws), a TTS WebSocket (api-reference/text-to-speech/stream) plus REST stream, an AsyncAPI spec (docs.sarvam.ai/asyncapi.json) and the Samvaad Voice Agents product (phone and chat agents, from Rs 3 a minute, LiveKit/Pipecat integrations). I did NOT test them with our key, so they are not used. How to use if wanted: server opens one WSS to the STT endpoint per session, forwards the 16 kHz PCM frames the browser already produces (send them over a browser WebSocket instead of one WAV per utterance), takes partial transcripts and the end-of-speech event, and feeds TTS text to the TTS WebSocket to start playing the first sentence before the rest is ready. Expected gain: most of the 0.3 to 1.7 s STT time, and about 1 s of TTS for long replies; the cached prompts are already 0 ms.
6. Dialogue translations are my own (see above). Slot readback says the requested time window, the booking line says the slot actually given (they differ in staggered mode).
